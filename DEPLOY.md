# Деплой в интернет - пошаговая инструкция

Локальный стенд (`README.md`) работает через ngrok-туннель - он временный
и живёт, пока сессия открыта. Этот документ - как поднять то же самое
(backend + Postgres + frontend + бот) на постоянном адресе.

Рекомендованный путь - **Railway**: один провайдер держит и backend, и
Postgres, и статику фронтенда, HTTPS-домен выдаётся автоматически (для
Telegram Mini App это обязательное требование), бесплатного тарифа хватает
для проверки на реальных пользователях. В конце - короткая альтернатива
на своём VPS, если нужен полный контроль или Railway не подойдёт по цене
при росте.

## Шаг 0. Подготовка (один раз, до деплоя)

1. **Закоммитьте текущий код**, если ещё не сделали - `git status` должен
   быть чистым. Деплой берёт код из git-репозитория.
2. Заведите аккаунт на [railway.app](https://railway.app) (можно через
   GitHub - тогда репозиторий сразу видно для подключения).
3. Держите под рукой значения для переменных окружения - они понадобятся
   на шаге 2:
   - `BOT_TOKEN` - из `backend/.env`, уже есть (токен `@wishhdesk_bot`).
   - `APIFY_TOKEN` - из `backend/.env`, уже есть.
   - `MINI_APP_URL` - пока не известен, заполните после шага 3.

## Шаг 1. Postgres

1. В Railway: **New Project → Database → PostgreSQL**. Создаётся сразу,
   без дополнительных настроек.
2. Откройте вкладку **Variables** у этой базы, скопируйте `DATABASE_URL`
   (формат `postgresql://...`) - понадобится на следующем шаге.

## Шаг 2. Backend (API + бот)

1. В том же Railway-проекте: **New → GitHub Repo**, выберите репозиторий
   `Вишлист-бот`.
2. В настройках сервиса задайте **Root Directory**: `backend`.
3. **Settings → Deploy**: задайте команды сборки/запуска, если Railway не
   определит их сам из `package.json`:
   - Build: `npm install && npx prisma generate && npm run build`
   - Start: `npx prisma migrate deploy && node dist/index.js`

   (`migrate deploy` накатывает миграции на реальную базу - в отличие от
   `migrate dev`, который используется только локально.)
4. **Variables** - добавьте все переменные из `backend/.env.example`:
   - `DATABASE_URL` - вставьте значение из шага 1.
   - `BOT_TOKEN`, `APIFY_TOKEN` - из вашего локального `.env`.
   - `PORT` - не задавайте вручную: Railway сам подставляет свой порт
     через переменную `PORT`, а `backend/src/index.ts` уже слушает именно
     её (`env.PORT`, биндится на `0.0.0.0`) - совместимо без правок кода.
   - `MINI_APP_URL` - временно поставьте любое значение (например
     `https://example.com`), обновите после шага 3.
   - **`ALLOW_DEV_TELEGRAM_ID` - НЕ добавляйте** (или явно `false`). Это
     дев-флаг для локальной разработки без настоящего Telegram - см.
     `backend/src/auth/telegramAuth.ts`. Если включить в проде,
     аутентификация через Telegram перестаёт хоть что-то проверять.
5. **Settings → Networking → Generate Domain** - Railway выдаст HTTPS-адрес
   вида `wishlistbot-backend-production.up.railway.app`. Это и есть адрес
   backend API.
6. Деплой запустится автоматически. Проверьте `https://<ваш-домен>/health`
   - должен ответить `{"ok":true}`.

## Шаг 3. Frontend

1. В том же проекте: **New → GitHub Repo** ещё раз, тот же репозиторий.
2. **Root Directory**: `frontend`.
3. Build: `npm install && npm run build`. Start: Railway для статики
   обычно предлагает **Static Site** - укажите папку `dist` как корень
   раздачи (или добавьте простой статик-сервер, если нужен Node-режим -
   для чистого Vite-SPA хватает статической раздачи).
4. **Variables**: `VITE_API_BASE` = адрес backend из шага 2, например
   `https://wishlistbot-backend-production.up.railway.app`.
5. **Generate Domain** - получите адрес фронтенда, например
   `wishlistbot-frontend-production.up.railway.app`.

## Шаг 4. Связать бота с новым адресом

1. Вернитесь в **Variables** backend-сервиса (шаг 2), обновите
   `MINI_APP_URL` на домен фронтенда из шага 3 (`https://...`).
2. Сохраните - Railway автоматически передеплоит backend с новым
   значением.
3. Откройте бота в Telegram (`@wishhdesk_bot`), нажмите /start - кнопка
   "Открыть вишлист-бот" должна вести уже на постоянный адрес, не на
   ngrok.

## Шаг 5. Проверка

Пройдите тот же путь, что в README ("Что реально работает"), но уже на
постоянных адресах: создание вишлиста, добавление позиции (в том числе
ссылку с Wildberries - проверяет, что `APIFY_TOKEN` доехал), "Поделиться",
бронь со второго Telegram-аккаунта, "Отметить купленным".

## О боте: long polling против webhook

`backend/src/index.ts` сейчас запускает бота через `bot.start()` (long
polling - бот сам ходит в Telegram за обновлениями). Для текущего
масштаба (проверка на реальных пользователях, не десятки тысяч) это
нормально работает и в проде, дополнительная настройка не нужна.
Переключение на webhook - это оптимизация под нагрузку, имеет смысл
отложить до реального роста числа пользователей.

## Не забыть после первого деплоя

- Секреты (`BOT_TOKEN`, `APIFY_TOKEN`, `DATABASE_URL`) теперь живут в
  Railway, а не только в локальном `.env` - доступ к дашборду Railway
  равносилен доступу к этим секретам.
- `ALLOW_DEV_TELEGRAM_ID` должен быть выключен в проде (см. шаг 2, п.4) -
  иначе аутентификация не защищает от подделки `telegramId`.

## Альтернатива: свой VPS

Если предпочитаете полный контроль или тариф Railway не подойдёт по цене
при росте - тот же стек (Docker Compose: Postgres + Node backend + Nginx,
отдающий собранный `frontend/dist`) разворачивается на любом VPS
(Timeweb, Selectel и т.п. - без иностранной привязки карты). Это отдельная,
более длинная инструкция (systemd/Docker, TLS-сертификат через Let's
Encrypt, настройка Nginx как reverse proxy) - скажите, если нужен именно
этот путь, распишу отдельно так же подробно.
