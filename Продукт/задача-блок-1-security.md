# Задача (БА): блок 1 - закрыть известные дыры безопасности

Источник - `Продукт/беклог-баги-итерация-1.md`, раздел High. Бот уже
живёт в проде с реальными пользователями (с 2026-10-01), поэтому из 10
High-пунктов в первую очередь берём те, что прямо сейчас дают постороннему
доступ к чужим данным или исполнению кода, а не просто кривой UX. Один
пункт - один отдел не делим, т.к. все четыре правки маленькие и находятся
в одних и тех же файлах бэкенда.

## Б-14. Сузить CORS + закрыть дыру в создании позиций

**Было:** `@fastify/cors` зарегистрирован с `origin: true` - отражает
любой Origin, значит любой сторонний сайт может дёрнуть API из браузера
жертвы. Отдельно: `POST /api/wishlists/:slug/items` вообще не проверяет
`telegramId` - **любой, кто знает slug чужого вишлиста (а slug специально
расшаривается дарителям), может молча добавить туда произвольные позиции**
от имени получателя. Это не было явно отдельным пунктом в беклоге, но
прямое следствие формулировки В-14 ("дёрнуть API от имени произвольного
telegramId") - в этом эндпоинте вообще нет проверки, от чьего имени.

**Нужно:**
- CORS origin - не `true`, а список: `env.MINI_APP_URL` (прод-домен
  фронтенда) + `http://localhost:5173` (локальная разработка).
- `POST /api/wishlists/:slug/items` - требовать `telegramId` (как в
  `DELETE /api/items/:itemId`) и проверять, что он совпадает с
  `wishlist.owner.telegramId`, иначе `403 not_your_wishlist`.

**Приёмка:** запрос с чужого Origin получает CORS-отказ в браузере;
`curl` на add-item с `telegramId` не-владельца вишлиста -> `403`; с
`telegramId` владельца или с валидной подписью `initData` владельца ->
`201`, как раньше.

## Б-8. `url` позиции принимает не-HTTP(S) схемы

**Было:** `z.string().url()` считает `javascript:alert(document.cookie)`
валидным URL (валиден синтаксически, схема не ограничена) - сохраняется и
отдаётся как есть, попадает в `href` на кнопке "Перейти в магазин"
(`ItemDetail.tsx`) с `target="_blank"`.

**Нужно:** в схеме `POST /api/wishlists/:slug/items` ограничить схему до
`http`/`https` (аналогично уже существующей клиентской проверке в
`AddItem.tsx`, но на бэкенде - клиентская не защищает от прямых запросов
к API).

**Приёмка:** `curl` с `url: "javascript:alert(1)"` -> `400
validation_error`; обычная `http(s)`-ссылка проходит как раньше.

## Б-15. ICS-фид календаря отдаёт чужие данные по одному `telegramId`

**Было:** `GET /api/calendar/:telegramId.ics` ищет пользователя
напрямую по `telegramId` без всякого секрета - `telegramId` не тайна
(виден в Telegram-группах, в URL профиля), значит теоретически можно
скачать чужой список сборов/взносов, подставив чужой id. Экран календаря
не подключён к итерации 1, но роут уже реально отвечает в проде.

**Нужно:** `.ics`-подписки по дизайну должны быть обычным URL, который
периодически дёргает внешнее приложение календаря (Apple Calendar,
Яндекс.Календарь) - значит авторизация через `initData` (как у остальных
роутов) здесь не подходит, нужен долгоживущий секрет в самом URL. Добавить
`User.calendarToken` (уникальная случайная строка, генерируется при
создании пользователя), заменить путь на
`GET /api/calendar/:token.ics`, искать пользователя по токену, а не по
`telegramId`.

**Приёмка:** `GET /api/calendar/<token>.ics` с настоящим токеном
пользователя -> `200` с тем же содержимым, что раньше по `telegramId`;
`GET /api/calendar/<любой telegramId>.ics` (старый путь) -> `404`, т.к.
роут с таким параметром больше не существует.

## Б-11. Текст бота обещает нереализованную фичу

**Было:** `/start` в `bot.ts` - "...скидывайтесь компанией на дорогой
подарок" - групповой сбор не подключён к экранам итерации 1 (см.
`README.md`), первое сообщение бота обещает то, что негде найти.

**Нужно:** убрать фразу про складчину из приветствия, оставить только то,
что реально есть - вишлист и бронь.

**Приёмка:** текст `/start` не упоминает сбор/складчину/скидывайтесь.
