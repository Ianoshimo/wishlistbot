## Роль организатора

Появляется вместе со сбором - в итерации 1 её нет. Организатор запускает
сбор без привязки к конкретному товару, чтобы группа могла собрать на
подарок дороже, чем может себе позволить один человек. Хочет видеть
текущую сумму и список тех, кто уже скинулся, чтобы не вести учёт вручную.
Хочет понятный исход для сбора, который не набрал сумму к сроку, чтобы
дарители доверяли инструменту.

## Требования

1. Сбор денег. Организатор создаёт сбор - с целевой суммой или без -
   не привязанный к конкретной позиции вишлиста. Дарители переводят через
   СБП, агрегатор - ЮKassa (ресёрч 2026-09-29 - см. `Контекст/`, официальная
   интеграция с Telegram Bot Payments API, подключение самозанятого без ИП,
   рабочий API возврата). Ни у одного агрегатора нет готового продукта
   "групповой сбор" - объединение N платежей одного сбора в один пул
   делаем на своей стороне, агрегатор видит независимые СБП-платежи.
   Прогресс и список внёсших видны всем участникам сбора.
2. Завершение сбора. У сбора есть явные конечные состояния - собран,
   истёк без сбора нужной суммы. При истечении срока без набора нужной
   суммы - полный автоматический возврат всем дарителям, без частичных
   вариантов и без решения организатора вручную. Обоснование: частичный
   возврат или разбирательство "куда делись деньги" - основной источник
   недоверия к сборам, автоворешение снимает вопрос доверия целиком.
   Организатор может продлить срок сбора до истечения, если сумма близка к
   цели. Техническая совместимость этого флоу с выбранным агрегатором -
   отдельный открытый вопрос ниже, юрист должен подтвердить до включения
   реальных платежей.

## Календарь и внешние интеграции

1. Экран "Календарь" - месячный вид с отметками на днях, где есть событие
   (срок сбора, дата повода), и список ближайших событий под ним. Тап по
   событию-сбору ведёт на экран сбора.
2. Поле "Дата повода" (необязательное) в создании сбора - без него
   календарю нечего показывать, кроме голого срока в днях. Не путать со
   "сроком сбора" (7/14/30 дней) - это разные вещи: дата повода
   информационная, срок сбора - действующий дедлайн для дарителей.
3. Подписка на внешний календарь - одна ICS/webcal-ссылка на пользователя,
   работает и с Apple/Mac Calendar, и с Яндекс.Календарём без отдельных
   интеграций под каждый (оба - стандартные подписчики iCalendar). В
   интерфейсе - две кнопки с понятными подписями ("Добавить в Apple
   Calendar", "Добавить в Яндекс.Календарь"), под капотом - один и тот же
   механизм.
4. Обратная синхронизация (правки в стороннем календаре видны у нас) - вне
   скоупа, требует отдельной оценки, если понадобится.

### Три варианта календаря по ролям

Один и тот же принцип (месячный вид + список + подписка на ICS/webcal),
но разное наполнение списка - роль определяет не форму экрана, а то, что
человеку нужно увидеть в первую очередь:

- **Получатель** [Calendar] - свои поводы и сборы, которые сам создал или
  за которыми следит (дни рождения друзей, чьи вишлисты видел). Смысл -
  не забыть о чужом поводе вовремя.
- **Даритель** [CalendarGiver] - взятые на себя обязательства: срок
  действия своих броней (с явным предупреждением, если скоро сгорит) и
  сборы, в которые уже внёс деньги. Смысл - не забыть довести до конца то,
  что уже начал.
- **Организатор** [CalendarOrganizer] - список всех сборов, которые он
  ведёт (может быть несколько параллельно, не обязательно на свой
  собственный повод - например, для нескольких коллег). Для каждого сбора
  виден статус "успевает/не успевает" относительно срока и цели, с
  возможностью продлить срок прямо из списка, без перехода на отдельный
  экран сбора. Смысл - командный пункт для того, кто одновременно ведёт
  не один сбор.

Разное наполнение - не разные технические механизмы: под всеми тремя один
и тот же ICS/webcal-фид (см. открытый вопрос про формат фида ниже), разница
только в том, что показывает интерфейс конкретной роли.

## Открытые вопросы

- Юрлицо, принимающее расчёты от ЮKassa - рекомендация по ресёрчу 2026-09-29
  (см. `Контекст/`) - ИП с самого старта, не самозанятый (передача сбора
  организатору юридически ближе к посредничеству, НПД это запрещает).
  Точная квалификация под 103-ФЗ - нужна консультация юриста, блокирует
  запуск с реальными деньгами, не блокирует то, что код уже написан.
- Поддерживает ли ЮKassa чек типа "добровольный взнос" без привязки к
  товару под 54-ФЗ - уточнить при подключении (юрист/бэкенд).
- Комиссия ЮKassa не возвращается при полном автовозврате - платформа несёт
  эту издержку с каждого возвращённого платежа, размер уточнить по
  финальному тарифу договора (финансы).
- Приватность чужих поводов в календаре - если у пользователя несколько
  вишлистов друзей с датами, видит ли он их дни рождения в своём календаре
  по умолчанию, или это включается отдельным согласием владельца повода
  (продукт).
- Формат ICS-фида - один агрегированный фид на пользователя со всеми его
  сборами, или отдельная подписка на каждый сбор - агрегированный проще
  для пользователя, но сложнее для отзыва доступа к одному конкретному
  сбору (бэкенд).
