### P0 - чинить сразу

**А-1. Владелец открывает свою ссылку из Telegram - бесконечные редиректы и пустой экран.**
- Приоритет / серьёзность / область: P0 / Critical / Фронт.
- Где: `frontend/src/pages/Home.tsx:35-44` (редирект по `start_param` при каждом монтировании `/`), `frontend/src/pages/SharedWishlist.tsx:36-40` (владельца отправляет на `/`), `frontend/src/telegram.ts:102-104` (`start_param` живёт всю сессию).
- Шаги: 1. Владелец тапает свою ссылку `t.me/wishhdesk_bot?startapp=w_<slug>` (например, проверить, как список выглядит у друзей). 2. Мини-апп открывается с `start_param=w_<slug>`.
- Ожидаемо: владелец видит свой редактируемый вишлист.
- Фактически: `/w/<slug>` → (это владелец) `/` → (есть `start_param`) `/w/<slug>` → ... Экран пустой, за 2 секунды 268 запросов `GET /api/wishlists/<slug>`, пока браузер сам не остановит навигацию.
- Влияние: первый сценарий после "Поделиться" (проверить свою ссылку) ломает приложение. Шторм запросов идёт на прод.
- Решение: обрабатывать `start_param` один раз за сессию (флаг в `sessionStorage` или модульной переменной). В `SharedWishlist` для владельца открывать нужный список (`localStorage[MY_SLUG_KEY] = slug`) без повторного разбора `start_param`.
- Критерии приёмки: открытие своей ссылки с `start_param` показывает свой вишлист за 1-2 запроса. Повторный переход на `/` в той же сессии не перекидывает на `/w/<slug>`.
- Подтверждение: воспроизведено, эмуляция Telegram `#tgWebAppData` с `start_param`. `SP/u5-owner-own-link-loop.png`, `SP/owner-loop.log`, гистограмма запросов в `SP/backend.log`.

**А-2. API сборов итерации 2 открыт в проде без авторизации.**
- Приоритет / серьёзность / область: P0 / Critical / Безопасность.
- Где: `backend/src/routes/pools.ts:16-117`, регистрация `backend/src/index.ts:48`. В роутах нет `resolveTelegramId`: `telegramId` берётся из тела как есть, а `/extend` не проверяет вообще ничего.
- Шаги: `POST /api/pools {"telegramId":"<любой>","title":"x","durationDays":7}` без заголовка `X-Telegram-Init-Data`. Затем `POST /api/pools/<id>/extend {"days":7}` и `POST /api/pools/<id>/contribute {"telegramId":"42","amount":100}`.
- Ожидаемо: 401 (или роутов нет, пока итерация 2 отключена).
- Фактически: 201 / 200 / 202. Создаются записи `User` для произвольных telegramId (`123456789`, `42`), пулы и "взносы" от чужого имени. Проверка подписи Telegram, введённая 2026-10-02, тут обходится.
- Влияние: любой может засорять прод-БД и создавать "пользователей" и "взносы" от чужого имени. Это задел под денежный функционал без защиты.
- Решение: не регистрировать `poolRoutes` (и экраны `/p/*`), пока итерация 2 выключена. Перед включением перевести роуты на `resolveTelegramId` и проверку организатора.
- Критерии приёмки: `POST /api/pools*` в проде отвечает 404 или 401. Новых записей `User` без подписанного initData не появляется.
- Подтверждение: воспроизведено curl, `SP/api-tests.log` п.8, 8b, 8c, 8d.

### P1 - до раздачи презентации

**А-3. Даритель, пришедший по ссылке, не может завести свой вишлист.**
- Приоритет / серьёзность / область: P1 / Critical / Продукт, Фронт.
- Где: `frontend/src/pages/SharedWishlist.tsx:104-198` (на экране нет ни одного входа в свой список), `frontend/src/pages/Home.tsx:35-44` (любой переход на `/` возвращает на чужой список, пока жив `start_param`).
- Шаги: 1. Даритель открывает `t.me/...?startapp=w_<slug>`. 2. Ищет, как создать свой вишлист. 3. Попадает на `/` (например, "Назад" с экрана "Такой страницы нет").
- Ожидаемо: есть заметный призыв "Создать свой вишлист", и `/` открывает собственный список.
- Фактически: на экране чужого списка только позиции. Нативная "Назад" со страницы 404 ("вернитесь к своему вишлисту") снова ведёт на `/w/<чужой slug>`.
- Влияние: ломается вирусная петля "получил ссылку → завёл свой" - главный канал роста и будущего юзербейза для экзита.
- Решение: CTA "Хочу такой же вишлист" внизу `SharedWishlist`. Разбор `start_param` один раз за сессию (общее решение с А-1).
- Критерии приёмки: с экрана чужого списка за 1 тап можно открыть свой (создаётся при первом заходе). `/` в той же сессии показывает свой список. Событие перехода пишется в аналитику.
- Подтверждение: воспроизведено с эмуляцией Telegram, `SP/giver-no-own-list.log`.

**А-4. Ошибка валидации в шторках не сбрасывается при исправлении поля.**
- Приоритет / серьёзность / область: P1 / Major / Фронт.
- Где: `frontend/src/components/AddItemForm.tsx:74-81`, `frontend/src/components/EditItemForm.tsx:92-132`. `setError(null)` вызывается только при следующем сабмите. Поля (`Field`, `onChange`) ошибку не трогают.
- Шаги: "Новая позиция" → ссылка → "Уже купил(а) сам(а)" → пустой номер → "Добавить" → ввести `+7 900 123-45-67`.
- Ожидаемо: баннер исчезает, как только поле исправлено.
- Фактически: баннер "Укажите номер телефона для перевода" висит под заполненным номером.
- Влияние: пользователь думает, что номер неверный, и бросает добавление (жалоба владельца).
- Решение: сбрасывать ошибку при изменении любого поля формы (или поля, к которому она относится). Ошибку поля показывать под самим полем.
- Критерии приёмки: после правки поля баннер клиентской валидации исчезает. Серверная ошибка исчезает при следующем изменении формы.
- Подтверждение: скриншот владельца `audit/3.jpg`. Воспроизведено в `SP/u2-add-error-stale.png`.

**Б-3. Нет глобального обработчика ошибок в Fastify (`app.setErrorHandler`

api.*()` не обёрнут в try/catch с показом ошибки пользователю

отправка невалидного URL или отрицательной цены на экране "Новая позиция"

что-то вообще.

**Б-5. Гонка при бронировании - нет атомарной проверки статуса.**
`resolveExpiredReservation` читает позицию, код проверяет `status !==
"available"` в JS, и только потом идёт отдельный `db.item.update` - между

двух дарителей возможна ситуация, когда оба запроса проходят проверку до
того, как первый успеет записать статус - двойная бронь на одну позицию,
то есть именно то, для защиты от чего эта фича вообще существует (см.
обоснование TTL в `CLAUDE.md`). Не пойман вживую (нужен точный тайминг),
но код однозначно допускает гонку - нужна проверка через нагрузочный тест
или переписать update на `updateMany({ where: { id, status: "available" }
})` с проверкой количества затронутых строк.

**Исправлено 2026-10-07 (ветка `chore/techdebt`).** Причина разобрана
живьём: Маркет ищет товар только по числовому id и игнорирует slug, не

запись `"productId","productSlug"` из JSON-состояния страницы, для
`/card/<slug>/<sku>` - `og:url` (там всегда настоящий slug и sku). Не тот
id, нет записи о товаре или slug без единого общего слова - превью
отбрасывается, название берётся из ссылки (`deriveNameFromUrl`, теперь
понимает `product--<slug>`). Ложное срабатывание деградирует безопасно -
до названия из ссылки, а не до чужого товара. Другие магазины проверка не

## Технический долг: найти бесплатное решение для фото с Wildberries
