# Вишлист-бот

Рабочее название проекта, может смениться.

## Суть

Телеграм-бот на базе мини-аппа: вишлист получателя + бронирование подарка
дарителем с переходом на маркетплейс + (со итерации 2) групповой сбор
денег на подарок. Международного стандарта, который объединяет всё это в
одном месте, на момент старта проекта нет - см. ресёрч конкурентов.

Целевой сценарий развития - не прибыль как самоцель, а рост до состояния
актива, который можно продать банку (экзит, банк покупает компанию с
юзербейзом). Важный нюанс из ресёрча: банку не нужна сама механика
перевода денег - она у него уже есть бесплатно (у Т-Банка/Альфы/ВТБ есть
встроенный "сбор денег"). Нужны событийные данные о желаниях и покупках
клиента, привязанные к поводу - этого у банка нет. Формулировать продукт
для покупателя как источник данных о покупательском намерении, а не как
платёжный функционал.

## Роли

- Получатель - ведёт вишлист.
- Даритель - бронирует позицию или скидывается в сбор.
- Организатор - запускает сбор (появляется только с итерации 2; может быть
  и сам получатель, и кто-то из дарителей - роль не привязана к аккаунту).

## Скоуп по итерациям (см. `Продукт/роадмап-5-итераций.md`)

Итерация 1 сужена 2026-09-29 до ядра: **только вишлист и бронь**, без денег
и без календаря - это дешевле всего проверить, ничего не упирается в
юрлицо/агрегатора. Деньги (групповой сбор через СБП/ЮKassa) и календарь -
итерация 2, полностью специфицированы, бэкенд и фронтенд уже написаны, но
не подключены к пользовательским экранам итерации 1.

Дальше: итерация 3 - партнёрки маркетплейсов и мультиповодность; итерация 4 -
реферальная виральность; итерация 5 - данные + пилот с банком + упакованный
актив для продажи.

## Ключевые решения (с обоснованием)

- Платёжная рельса - СБП, нейтрально, без привязки к конкретному банку на
  старте - чтобы не отдавать рычаг торга одному потенциальному покупателю.
- Агрегатор для сбора - ЮKassa (не Т-Kassa, не Robokassa) - официальная
  интеграция с Telegram Bot Payments, принимает самозанятого без ИП,
  рабочий API возврата. Детали - `Контекст/ресёрч-агрегаторы-2026-09-29.md`.
- Юрлицо для потока сбора денег - ИП с самого старта, не самозанятый:
  передача накопленного сбора организатору юридически ближе к
  посредничеству, а 422-ФЗ это самозанятым запрещает. Партнёрский доход с
  маркетплейсов - самозанятый достаточен. Детали -
  `Контекст/ресёрч-юрлицо-2026-09-29.md`.
- TTL брони - 5 дней; личность дарителя не раскрывается никому, включая
  получателя (как у Amazon) - защита сюрприза, не только от задвоения.
- При недоборе суммы сбора - полный автоматический возврат всем, без
  частичных вариантов - снимает вопрос доверия целиком.
- Календарь - одна ICS/webcal-подписка на пользователя, а не отдельные
  интеграции с Apple Calendar и Яндекс.Календарём - оба понимают один
  стандарт.

- **Синхронизация календарей - продуктовое решение + реализация**
  (2026-10-02, по просьбе пользователя "продумай бизнесово... и
  реализуй") - старая версия (`routes/calendar.ts`, экраны
  `Calendar{Recipient,Giver,Organizer}.tsx`) была построена вокруг
  `Pool` (групповой сбор денег, итерация 2, отключена от экранов) и
  показывала бы пустоту вообще всем в итерации 1 - подключать её как
  есть не было смысла. Вместо этого:
  - **Повод живёт на `Wishlist`** (`occasionTitle`/`occasionDate`, новые
    поля), не на `Pool` - не требует денег/сбора, работает уже сейчас.

    вишлист) - один тап/скачивание, без авторизации и подписки, видно

    повторяющийся календарь почти никто не заводит ради одного дня
    рождения одного друга, а "добавить в календарь" одним тапом - да.

    (`GET /api/calendar/:token.ics`, переиспользует уже существовавший
    `User.calendarToken`) - агрегирует поводы **всех** вишлистов, где
    этот человек реально дарил (забронировал позицию или
    присоединился к доле в "скинуться"), не только текущего. Решает
    открытый вопрос приватности из CLAUDE.md ("видит ли пользователь
    чужие поводы по умолчанию") - видит только то, к чему реально
    причастен, не чужие дни рождения случайных людей. Ссылка -
    `webcal://` (сама открывается в приложении календаря) + копия
    `https://` рядом на случай, если календарь не понимает `webcal`.
  - **.ics собран по RFC 5545 с умышленными деталями под реальное
    использование, не просто "событие на дату"**: `VALUE=DATE`
    (весь день, не точное время), `RRULE:FREQ=YEARLY` (поводы обычно
    годовые - без этого напоминание сработало бы один раз и исчезло
    бы из календаря на следующий год), `VALARM` за 3 дня до даты
    (успеть выбрать и купить подарок, а не просто увидеть дату в день
    икс), `URL`/`DESCRIPTION` обратно на вишлист. Общая логика -
    `services/ics.ts`, используется и разовым, и агрегатным фидом.
  - **Живой баг, найден и исправлен при проверке** - ссылка на `.ics` в
    обоих местах (разовая и подписка) строилась через `API_BASE`,
    который **в локальной разработке нарочно пустой** (`.env`,
    полагается на прокси `/api` в `vite.config.ts` - это специально,

    которую копируют в другое приложение или открывают отдельной
    вкладкой, относительный путь бесполезен - он не значит ничего вне
    текущей страницы. В проде `VITE_API_BASE` всегда абсолютный
    (`DEPLOY.md`), поэтому раньше это нигде не всплывало. Добавлена
    `absoluteApiUrl()` в `api.ts` - в деве подставляет
    `window.location.origin`, если `API_BASE` пуст.
  - Проверено по HTTP целиком (повод выставлен/снят, разовый `.ics`
    валиден и парсится по RFC 5545, агрегатный фид корректно собирает
    повод вовлечённого вишлиста и пуст для постороннего без вовлечения
    - граница приватности подтверждена) и в браузере (иконка/бейдж
    повода, bottom sheet с формой и подпиской, кнопка "В календарь" на
    экране дарителя, абсолютность ссылки после фикса).

    их роуты не тронуты - остаются в коде под итерацию 2, когда дойдут

    /api/wishlists` раньше был идемпотентным "найди-или-создай" именно
    затем, чтобы потеря localStorage (переустановка, автоочистка
    WebView) не плодила дубликат поверх уже существующего списка.
    Теперь каждый вызов создаёт НОВЫЙ список - так и должно быть для
    кнопки "+". Восстановление при потере localStorage переехало на

    владельца, `MyWishlist.tsx` сначала смотрит, что уже есть

    пересланную ссылку, поэтому всегда работает с первым/единственным.

    четвёртого, переименование (+ 403 при попытке чужим telegramId),

    (эмуляция переустановки) → Onboarding → "Создать свой вишлист" →
    восстановились оба существующих списка под своими именами, новый
    дубликат не появился (проверено и по API - count не вырос).
  - Заголовки `MyWishlist`/`SharedWishlist` теперь показывают
    `wishlist.title` вместо жёстко зашитого "Мой вишлист"/"Вишлист".
  - Удаления вишлиста как такового по-прежнему нет (только позиций
    внутри) - не просили, не делал.
